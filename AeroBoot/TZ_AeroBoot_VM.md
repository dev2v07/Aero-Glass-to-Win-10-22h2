# ТЗ: AeroBoot — безопасное тестирование в VirtualBox

## 1. Контекст и обязательные источники

Проект: `C:\projects\Aero Glass`.

Перед началом работы новый чат обязан прочитать:

1. `C:\projects\Aero Glass\AGENTS.md`;
2. `C:\projects\Aero Glass\HANDOFF.md` — особенно записи про HackBGRT, AeroBoot и диагностику Explorer;
3. `C:\projects\Aero Glass\AeroBoot\README.md`;
4. `C:\projects\Aero Glass\AeroBoot\AeroBoot.c` и `AeroBoot.inf`;
5. `C:\projects\Aero Glass\Scripts\Validate-AeroBootAnimation.ps1`.

Текущая база: прототип `AeroBoot` добавлен, но EFI-бинарник ещё не собран и на реальную систему не устанавливался. Кадры `activity000.bmp`...`activity104.bmp` проверены: 105 файлов, 200x200, 24-bit BMP, без сжатия, около 7 секунд анимации при 15 FPS.

## 2. Цель

Создать и проверить собственный `AeroBoot.efi`, который в тестовой UEFI-виртуальной машине:

- получает GOP;
- находит ESP, с которой запущен;
- показывает полную цепочку кадров Windows 7 из `AeroBoot\\animation`;
- после анимации передаёт управление Windows Boot Manager;
- при любой ошибке безопасно переходит к оригинальному загрузчику;
- не перезаписывает `\\EFI\\Microsoft\\Boot\\bootmgfw.efi`.

На этом этапе не требуется подключать AeroBoot к GUI Aero Glass или менять загрузку основной Windows.

## 3. Жёсткие ограничения безопасности

- Работать только с виртуальной машиной VirtualBox `TEST AERO`.
- Не запускать установщик, EFI-скрипты или команды изменения NVRAM на хосте.
- Не использовать реальный EFI-раздел хоста и не менять BCD хоста.
- Перед любым изменением виртуального диска создать snapshot VirtualBox: `AeroBoot-before-test`.
- Secure Boot в VM оставить выключенным до отдельного этапа подписи.
- Не применять HackBGRT и `Win7BootUpdater` к хосту.
- Не копировать `AeroBoot.efi` в `C:\\Windows`, `C:\\EFI` или на системный ESP хоста.
- Любая команда установки должна сначала показывать точный путь диска/ESP и быть явно ограничена VM.
- При сбое тест прекращается, VM выключается, затем выполняется откат snapshot.

## 4. Этапы работы

### Этап A — подготовка

1. Проверить, что VM `TEST AERO` работает в режиме UEFI.
2. Зафиксировать версию Windows, тип прошивки VirtualBox, Secure Boot и состояние snapshot.
3. Выполнить проверку кадров скриптом `Scripts\\Validate-AeroBootAnimation.ps1`.
4. Найти EDK II BaseTools и собрать `AeroBoot` как `UEFI_APPLICATION`.
5. Если toolchain не найден, не имитировать сборку: сообщить точную блокирующую зависимость и способ её установить.

### Этап B — безопасный стенд VM

1. Внутри VM определить букву ESP и сохранить резервные копии только внутри VM.
2. Создать на ESP тестовый каталог `\\EFI\\AeroBoot\\`.
3. Скопировать туда только тестовый бинарник и кадры.
4. Сохранить оригинальный Windows Boot Manager в отдельный файл VM, например `\\EFI\\AeroBoot\\bootmgfw-original.efi`.
5. Использовать отдельную тестовую загрузочную запись VM или временный UEFI shell-запуск, не заменяя штатный файл Microsoft.
6. Перед первым запуском сохранить вывод `bcdedit /enum firmware` внутри VM и состояние ESP.

### Этап C — функциональный тест

Проверить минимум:

1. VM загружается через AeroBoot.
2. Отображается первый кадр без обрезки и неправильного цвета.
3. Проигрываются все 105 кадров строго по порядку.
4. Нет зависания на отсутствующем кадре.
5. После последнего кадра запускается Windows.
6. Перезапуск VM повторяет цепочку.
7. Принудительное удаление/переименование одного кадра вызывает безопасный chainload без зависания.
8. Неподдерживаемый BMP вызывает безопасный chainload.
9. Откат snapshot возвращает обычную загрузку Windows.

### Этап D — отказоустойчивость

Проверить сценарии отказа GOP, файловой системы, отсутствующего кадра и недоступного оригинального загрузчика. Для каждого сценария должен быть понятный результат в журнале и автоматический переход к штатному `\\EFI\\Microsoft\\Boot\\bootmgfw.efi`, если это возможно.

## 5. Что нужно доработать в коде

- Добавить ограниченный EFI-лог: этап запуска, найденный GOP, количество кадров, номер проблемного кадра, результат chainload.
- Добавить таймаут анимации и аварийный chainload, чтобы VM не зависала бесконечно.
- Проверять переполнение при вычислении размеров BMP и выделении памяти.
- Проверять размер файла до чтения в память.
- Явно проверять `bfType`, `biBitCount`, `biCompression`, ширину, высоту и размер строки BMP.
- Не использовать бесконечные циклы без watchdog/таймаута.
- Не менять штатный Windows Boot Manager.
- Добавить скрипт проверки VM-артефактов и отчёта после теста.

## 6. Критерии приёмки

Работа считается выполненной только если:

- есть воспроизводимый `.efi`-бинарник и указано, каким toolchain он собран;
- тест пройден именно в VM `TEST AERO`;
- показаны фактические фото/скриншоты или видеозапись загрузки с полной цепочкой;
- Windows после анимации загружается;
- отказ одного кадра не блокирует загрузку;
- snapshot откатывает тест без остаточных изменений;
- проверены ESP, UEFI-записи и BCD VM до и после;
- результат и все изменения записаны в `HANDOFF.md` с путём snapshot и артефактами;
- отдельно указано, что на хост-системе EFI/BCD/NVRAM не изменялись.

## 7. Формат отчёта нового чата

В конце добавить в `HANDOFF.md`:

- дата и время;
- VM и snapshot;
- toolchain и команда сборки;
- SHA-256 `AeroBoot.efi`;
- список тестов и фактический результат каждого;
- состояние загрузки VM после тестов;
- пути резервных копий и лога;
- ограничения и нерешённые проблемы;
- подтверждение: хостовая Windows и её EFI-раздел не изменялись.

Нельзя писать «работает», если проверена только сборка. Сборка, запуск в UEFI и успешный chainload — три разные проверки.
