# ТЗ: полный аудит, исправление ошибок и оптимизация Aero Glass

## 1. Цель

Провести полный технический аудит текущего проекта Aero Glass и довести заменённую оболочку Windows до стабильной работы без заметных задержек, зависаний, падений и лишней нагрузки на `explorer.exe`, рабочий стол и DWM.

Цель — не просто успешная сборка, а подтверждённая работа на реальной Windows 10 Pro 19045 x64 с сохранением функциональности Aero Glass и Aero Glass Start Menu.

## 2. Обязательные источники перед началом

Новый агент обязан сначала прочитать:

1. `C:\projects\Aero Glass\AGENTS.md`;
2. `C:\projects\Aero Glass\HANDOFF.md` полностью или по всем записям, связанным с текущей задачей;
3. этот файл;
4. структуру `OpenGlass`, `OpenGlassHost`, `OpenGlassGUI`, `OpenGlassStartMenu`, `Common`, `Scripts`;
5. актуальные диагностические логи Windows и результаты предыдущих проверок.

Нельзя считать старые сообщения или скриншоты доказательством текущего состояния. Все важные выводы нужно подтвердить свежей проверкой.

## 3. Жёсткие ограничения

- Не отключать OpenGlass, Aero Glass Start Menu, службу, автозапуск или функции оболочки только для получения красивого графика нагрузки.
- Не удалять функции, атласы, темы, курсоры или настройки без отдельного согласования.
- Не менять системные DLL Windows.
- Не внедрять новые хуки в DWM или Explorer без анализа жизненного цикла, ABI и отката.
- Не выполнять `git reset --hard`, массовое удаление или перезапись пользовательских изменений.
- Перед изменениями создать резерв исходников/конфигурации в `C:\projects\Aero Glass\_backups\` и записать путь в `HANDOFF.md`.
- Каждую правку, сборку, проверку, найденную проблему и ограничение записывать в `HANDOFF.md`.
- Любой системный эксперимент должен быть обратимым и выполняться только после фиксации исходного состояния.

## 4. Инвентаризация текущего состояния

Составить таблицу фактических компонентов:

- путь, версия, размер и SHA-256 каждого используемого EXE/DLL;
- какие процессы запущены: `AeroGlass.exe`, `OpenGlassHost.exe`, `OpenGlassStartMenu.exe`, `explorer.exe`, `dwm.exe`;
- какие службы, задачи автозапуска и registry-настройки относятся к Aero Glass;
- какие DLL загружены в `explorer.exe` и `dwm.exe`;
- какой бинарник реально загружен, а не только присутствует в каталоге сборки;
- какой toolset использован для каждой сборки;
- поддерживаемая версия Windows и архитектура.

Отдельно проверить, что удалённый старый Classic Shell не является обязательной runtime-зависимостью. Наше меню должно использовать собственные бинарники и ресурсы, а не запускать старую установку Classic Shell.

## 5. Аудит ошибок и падений

Проверить свежие события за несколько запусков и перезапусков:

- Application Error;
- Application Hang;
- Windows Error Reporting;
- Service Control Manager;
- Explorer/WER;
- DWM и Winlogon.

Для каждого события определить:

- процесс и модуль-виновник;
- воспроизводимость;
- действие пользователя, после которого возникает ошибка;
- является ли это реальной причиной или побочным событием;
- минимальный безопасный способ исправления;
- способ проверки после исправления.

Особенно проверить ранее обнаруженные классы проблем:

- `OpenGlassStartMenuDLL.dll_unloaded`;
- ошибки повторной инициализации Start Menu после перезапуска;
- зависание/задержку закрытия GUI;
- падения или fast-fail `OpenGlassHost.exe`;
- зависания `explorer.exe`;
- ошибки уведомления DWM и жизненного цикла хуков.

## 6. Аудит Start Menu DLL

Проверить:

1. загрузку DLL в Explorer;
2. повторный запуск `OpenGlassStartMenu.exe` без перезагрузки Windows;
3. закрытие меню и приложения настроек;
4. открытие настроек из контекстного меню кнопки «Пуск»;
5. повторное открытие встроенных настроек;
6. смену языка, стиля, кожи, кнопки Start и пользовательских ресурсов;
7. корректное завершение без `FreeLibrary` во время активных callbacks;
8. освобождение hooks, subclass, timer, окон и потоков;
9. отсутствие повторной установки одного и того же hook;
10. поведение после перезапуска Explorer.

Проверить гонки между GUI, `OpenGlassStartMenu.exe`, DLL и Explorer. Для каждой callback-функции определить владельца памяти и момент, когда она гарантированно больше не может выполняться.

## 7. Аудит нагрузки и задержек

Измерить базовое состояние до изменений и после каждой существенной правки.

Сценарии:

- простой рабочий стол без действий 60 секунд;
- открыть/закрыть меню «Пуск» 20 раз;
- открыть контекстное меню кнопки «Пуск» 10 раз;
- открыть настройки, переключить разделы, закрыть;
- открыть и закрыть 10 окон Explorer;
- перезапустить Explorer;
- сменить светлую/тёмную тему;
- применить настройки стекла;
- выбрать кнопку Aero/Classic/Другое;
- включить/выключить прозрачность и пользовательскую текстуру;
- открыть несколько окон и переключаться между ними.

Для каждого сценария зафиксировать:

- время запуска приложения;
- время открытия меню и настроек;
- время закрытия приложения;
- CPU и private working set `explorer.exe`, `dwm.exe`, `OpenGlassHost.exe`, `OpenGlassStartMenu.exe`, `AeroGlass.exe`;
- количество потоков и handles;
- количество загруженных DLL;
- наличие роста памяти после повторения сценария;
- визуальные задержки, мигание, недорисовки и зависания.

Не делать вывод о нагрузке по одному снимку. Для каждого показателя использовать повторяемый baseline и минимум три замера.

## 8. Поиск источников задержек

Проверить код на:

- `Sleep` и фиксированные задержки в UI/hook-пути;
- синхронное чтение файлов и реестра в UI-потоке;
- повторную загрузку PNG/BMP/атласов без кэша;
- лишние перерисовки и `Refresh/Update/Layout` в циклах;
- таймеры, которые работают постоянно без необходимости;
- polling вместо событий;
- блокировки, удерживаемые во время callback;
- ожидание завершения потоков при закрытии окна;
- утечки GDI/USER/DWM ресурсов;
- повторную установку subclass/hook;
- загрузку DLL на каждый клик;
- рекурсивные уведомления `WM_THEMECHANGED`;
- работу с Explorer из неподходящего потока;
- операции с registry, выполняемые синхронно при каждом открытии меню.

Оптимизировать только после подтверждения профилировкой или воспроизводимым измерением.

## 9. Проверка настроек и фактического применения

Для каждой видимой настройки проверить цепочку:

`контрол UI → сохранённое значение → runtime-читатель → уведомление → фактический эффект → откат`.

Минимальный набор:

- стиль Start Menu;
- кнопка Aero/Classic/Другое;
- путь пользовательского изображения кнопки;
- прозрачность панели задач;
- цвет и текстура панели задач;
- тема/атлас;
- отражение и материал;
- светлая/тёмная схема GUI;
- курсоры;
- профили и резервирование;
- встроенное окно настроек;
- автозапуск и восстановление после перезапуска.

Если настройка отображается в UI, но не меняет Windows, это считать дефектом, а не косметическим недочётом. Нужно либо реализовать фактическое применение, либо явно пометить функцию как неподдерживаемую и записать причину.

## 10. Сборка и статические проверки

Выполнить по возможности:

```powershell
msbuild OpenGlass.slnx /m /restore /p:Configuration=Release /p:Platform=x64
msbuild OpenGlassTests/OpenGlassTests.vcxproj /m /p:Configuration=Release /p:Platform=x64
.\Build\x64\Release\common\OpenGlassTests.exe
git diff --check
```

Если отдельный legacy-компонент требует v143 из-за ATL/MFC, это нужно явно зафиксировать: какой проект собран на v143, почему v145 невозможен, какой бинарник установлен и каким SHA-256 проверен.

Не считать успешную сборку доказательством стабильности инъекции или Explorer. Эти проверки должны быть разделены.

## 11. Реальная проверка после исправлений

После сборки:

1. сохранить SHA-256 установленного бинарника;
2. проверить фактические загруженные модули;
3. выполнить холодный запуск Windows;
4. проверить автозапуск;
5. открыть и закрыть Start Menu минимум 20 раз;
6. перезапустить Explorer минимум 3 раза;
7. перезапустить Aero Glass Start Menu минимум 3 раза;
8. проверить GUI и встроенное окно настроек;
9. проверить отсутствие новых записей Application Error/Application Hang;
10. повторить измерения нагрузки и сравнить с baseline.

Нельзя перезапускать или останавливать системные компоненты без записи исходного состояния и причины. При проверке не отключать функции, которые пользователь попросил сохранить.

## 12. Критерии приёмки

Работа считается завершённой только если:

- нет воспроизводимых падений в перечисленных сценариях;
- Explorer и рабочий стол остаются отзывчивыми после длительного простоя и повторных действий;
- нет непрерывного роста CPU, памяти, handles или GDI/USER-ресурсов;
- Start Menu и Explorer корректно переживают перезапуск;
- настройки реально применяются и откатываются;
- GUI не мигает и не зависает при сохранении;
- фактически загруженные DLL соответствуют собранным артефактам;
- каждый исправленный дефект имеет тест до/после;
- сборка, тесты, ограничения и нерешённые проблемы записаны в `HANDOFF.md`;
- отдельно указано, какие проверки выполнены на реальной системе, а какие только статически или в VM.

Фраза «оптимизировано» допустима только при наличии сравнения baseline до/после. Если проблема не воспроизведена, писать «не воспроизведено», а не «исправлено».

## 13. Обязательный формат записи в HANDOFF.md

Для каждой правки:

- дата и время;
- симптом;
- подтверждённая причина или статус «причина не подтверждена»;
- изменённые файлы;
- резервная копия;
- команда сборки;
- бинарник и SHA-256;
- тестовый сценарий;
- фактический результат;
- влияние на Explorer/DWM/рабочий стол;
- способ отката;
- оставшиеся риски.
